# Cards remember which trackers they were sent to

- Problem: cards stay on the page after Submit and survive a refresh, so pressing Submit again logged the same hours twice in Redmine, Jira or ClickUp.
- Data: each card may carry `sentTo: { redmine?: true, jira?: true, clickup?: true }`; absent means nothing sent. It is saved with the card (`helpers/cardsStorage.js` accepts an object of `true` values and rejects anything else). Pure helpers: `helpers/sentMarks.js`.
- Marking: `submitWorklogRequests(requests, service, { onSuccess })` calls `onSuccess(request)` the moment that one request fulfils, before the batch ends. The three send actions take `{ onCardSent }` and put the card id on each request (what is sent to the tracker is unchanged). The store action `markCardsSent(service, ids)` marks, so the card is saved at once; with 3 of 5 sent, those 3 are marked and a retry sends the other 2. The demo build marks too.
- Filters: `filterWorklogsForRedmine`, `filterWorklogsByTask` (Jira) and `filterWorklogsForClickUp` skip cards already sent to that tracker. The dialogs say "N of M cards were already sent to <tracker> and will be skipped." and, when nothing is left, "All cards with a <field> were already sent to <tracker>." (Confirm stays disabled).
- Generate: cards generated from Redmine, Jira or ClickUp are marked for that tracker (they already exist there). File import marks nothing. `isJiraExport` / `isClickUpExport` are only stored and saved; nothing reads them, so they never guarded a send.
- On the card: "Sent: Redmine, ClickUp", each name with a small control (`Send to <tracker> again`) that clears only that mark, for an entry deleted in the tracker. Editing keeps the marks (the app does not update tracker entries); the card says so while edited. Moving a day or changing a date keeps them. `updateWorkLog` ignores a `sentTo` in the edited data and keeps the store's own.
- Two tabs, marks: a tab remembers the marks it made, for 30 s, and puts them back on an incoming snapshot that lacks them (then saves). A save caused by marking first merges in the marks already saved by another tab. "Send again" removes the mark from that memory. The 30 s limit keeps another tab's deliberate "Send again" from being undone.
- Two tabs, sending: each Submit runs inside `navigator.locks.request('worklog-hub:submit:<ownerId>:<service>', { ifAvailable: true })` (`helpers/submitLock.js`). A taken lock shows "Already sending to <tracker> in another tab." and sends nothing. Inside the lock the saved marks are read again and cards sent meanwhile are dropped from the set the dialog showed. Without `navigator.locks` the send just proceeds.
- Not done: duplicates are not detected by reading the trackers. A request that fails on the network after the tracker saved the entry is not marked (the error text already says to check before retrying).
